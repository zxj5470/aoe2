# AI 连接大脑，通过代替思考

惯例，阅读本文大约需要 2.5 分钟。

最近在搞一个帝国时代2前端复刻版，用 Three.js 做的。

前置内容：

* HUD 重构 - HUD 就是游戏界面，包括顶部标题栏、下方命令栏、右下角小地图。这玩意有 1691 行，太臃肿了，所以重构。
* 资源管理功能 - 玩过帝国时代的都知道，四种资源：食物、木头、黄金、石头。。

## 看起来完美

HUD 重构，我让 AI 拆一下。

好家伙，拆得那叫一个漂亮：

- ResourceDisplay.js 负责资源显示
- Minimap.js 负责小地图
- InfoPanel.js 负责信息面板
- ActionPanel.js 负责建筑面板

每个模块职责清晰，代码整洁。看起来完美。

## 然后打脸来了

我需要"加个升级时代的按钮"。需要获取玩家当前时代和资源。然后我就看到了这玩意：

```javascript
// 系统一：ResourceManager
game.resourceManager.addResource('wood', 1000);

// 系统二：Player
game.player.addResource('wood', 1000);
```

两套资源系统。各自完整。各自独立。**各自毫无关系**。

我整个人都麻了。

回过头看，AI 创建 ResourceManager 的时候没问"Player 要不要持有资源"，创建 Player 的时候也没问"ResourceManager 已经存在了还要不要重复"。

更离谱的是初始化：

```javascript
this.resourceManager = new ResourceManager();  // 资源从 0 开始
this.player = new Player({ gold: 100, ... });  // 这 100 金币去哪了？？？
```

Player 初始化传进去的资源值，**直接被无视了**。因为 UI 绑的是 ResourceManager。

等于我传了个寂寞。

## 问题根源

仔细想想，AI 根本不知道这两个模块应该有关系。

你让 AI 写资源管理模块，它写完了，功能齐全。
你让 AI 写玩家模块，它写完了，有 ID、有名字...还有一套资源属性。

**它只管"现在有没有"，不管"以后怎么办"。**

资源属于谁？玩家。
玩家有几种颜色？以后会有多人模式。
观战模式要切换视角？那是后面的事。

这些**耦合关系**，AI 完全没概念。

## 解决方案

我提了个方案 C：

> ResourceManager 应该是 Player 的属性，资源本来就是跟玩家绑定的。以后观战模式要切换玩家视角。

```
Game
└── Player
    ├── id, name, ageLevel
    ├── resourceManager  ← 资源管理器属于玩家
    └── units[]
```

最终的代码就成了这样。
```js
game.player.resourceManager.addResource('wood', 1000);
```
语义清晰，扩展性强，没有重复。但 AI 压根没主动提过这个方案。它就在那两个破系统之间打补丁。然后就和狗熊掰棒子一样，捡一个丢一个。

## 总结
所以就是目前的 AI 编程仍然有很多致命缺陷：

**它只会在你给它的任务范围内找 “他认为是的” 最优解。**

| 场景 | AI 的操作 | 结果 |
|------|----------|------|
| 创建新类 | 把所有"可能用到"的功能都实现一遍 | 跟现有系统撞车 |
| 重构代码 | 模块内部优化得飞起 | 模块之间是什么关系？管不了 |
| 加功能 | 你要什么给什么，它就按你的要求来，甚至直接面向你的“测试用例”编程 | 跟现有设计冲不冲突？不关我事 |

## 还有另一个问题：“智驾依赖”
网上都在玩梗，自动驾驶事故前 0.1 秒退出智驾。编程领域也一样。
AI 用得太顺手了，我发现自己开始"无脑过过过"：

- 代码生成了？过。
- 测试通过了？过。
- 功能实现了？过。
- AI 说没问题？那就没问题。

**那我直接AI连通大脑，通过替代思考**

以前写代码，每一步都得自己想：

- 这个模块跟那个模块什么关系？
- 这个属性放哪里合适？
- 以后扩展怎么办？
- 有没有更合理的设计？

现在？AI 给啥我用啥，反正能跑。出了问题？让 AI 修。修好了？继续过。

就像开了智驾的车主，一开始还紧张地盯着路面，后来就开始玩手机、打瞌睡。反正车自己会开。
然后某天，系统功能崩了，你改不上来，每个模块写的都非常好注释拉满，精细的就像米其林餐厅做出来的美食。每个模块看起来都没有问题，但是加在一起就有问题。

两套资源系统，数据对不上，UI 显示错误。这时候才想起来：哦，我好像从来没审视过整体架构。

可怕的点在于这是**温水煮青蛙**

一开始你只是让 AI 帮你写个小函数。后来让它写个模块。再后来让它重构。最后你发现，整个项目你都不太熟了。


代码是你写的吗？是 AI 写的。你只是点了"过"。

AI 接管了你的键盘，但**不能让它接管你的脑子**。
某种意义上来说上个版本的AI还相对可控，我把它称之为为 ACC自适应驾驶。ACC 你还需要控制方向盘，只是不需要手动控制油门刹车了，直接按加减最高速度就行了。

## 最后说两句

AI 写代码确实快，但它有个根本问题：**它优化的是你给它的任务，不是你的整个系统。**

就像个只看眼前三步的棋手，每一步都走得挺对，但整盘棋已经输了。

所以：

1. **架构意识得自己保持**：别被局部优化忽悠了
2. **定期跳出来看看**：别光埋头写代码，看看整体结构
3. **别光看代码，问设计**：多问"为什么"比问"怎么做"重要

AI 能帮你写出完美的函数，但系统设计？**那是你自己的事。**

---

结论：编程的本质就是填坑。从需求到设计、从设计到实现、从实现到重构，哪一步不是在填之前挖的坑？AI 能帮你挖坑填得快一点，但坑在哪、怎么填，还是得你自己看。
